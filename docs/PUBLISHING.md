# Публикация сборок и обновлений в AbiLauncher через GitHub

## 1. Структура репозиториев на GitHub

AbiLauncher работает с **публичными** GitHub-репозиториями и не требует встроенных токенов в приложении.

### А. Репозиторий каталога (`Abi_Launcher`)

Хранит общий список официальных сборок в файле [`catalog/catalog.json`](../catalog/catalog.json):

```json
{
  "schemaVersion": 1,
  "name": "Официальный каталог AbiLauncher",
  "packs": [
    {
      "repo": "AbiBok89/abi_tfg",
      "branch": "main",
      "path": "launcher/pack.json"
    }
  ]
}
```

Адрес этого файла настраивается в **Настройки -> Источники сборок GitHub** (по умолчанию указывает на `raw.githubusercontent.com/AbiBok89/Abi_Launcher/main/catalog/catalog.json`). Игрок также может добавлять сторонние репозитории сборок вручную.

### Б. Репозиторий конкретной сборки (например `AbiBok89/abi_tfg`)

Рекомендуемая структура:

```text
<repo>/
  launcher/
    pack.json       # Описание сборки, версии, обложка, сервер, ссылка на manifest.json
    news.json       # Новости конкретной сборки
    cover.png       # Обложка (PNG/JPEG/WebP, до 5 МБ)
  ...               # (по желанию) исходные конфиги/скрипты сборки в Git
```

А сами файлы версии сборки (`manifest.json`, `pack-part-01.zip`, крупные `.jar` и ресурспаки) публикуются в **GitHub Releases** этого же репозитория!

> [!NOTE]
> Для обратной совместимости с уже существующим `AbiBok89/abi_tfg` лаунчер умеет читать и корневой `launcher-index.json`, если `launcher/pack.json` отсутствует (HTTP 404).

## 2. Как учитываются ограничения GitHub

1. **Размер файлов в Git**: GitHub ограничивает размер файла в самом Git-репозитории (предупреждение от 50 МБ, блокировка от 100 МБ). Поэтому тяжёлые моды и ресурс-паки выносятся в **GitHub Releases**, где лимит на один файл — **2 ГБ**.
2. **Частота запросов (Rate Limit) и тысячи мелких файлов**: В крупных сборках (таких как TerraFirmaGreg-Modern) более 15 000 файлов (KubeJS, конфиги, скрипты, модели). Скачивать их поштучно через `raw.githubusercontent.com` неэффективно и приводит к троттлингу.
   Утилита `npm run pack-tool` автоматически:
   - упаковывает все мелкие файлы (`< 4 МБ`) в несколько архивов `pack-part-01.zip`, `pack-part-02.zip` (до 150 МБ на часть);
   - копирует крупные файлы (`>= 4 МБ`) как отдельные ассеты релиза;
   - записывает в `manifest.json` **индивидуальный путь, размер и SHA-256 для каждого файла**, даже если он лежит внутри `pack-part-XX.zip`.
3. **Ускорение повторных проверок**: перед запуском лаунчер скачивает только `pack.json` и `manifest.json` (два запроса), сравнивает их с фактическими файлами на диске и скачивает только изменённые или недостающие файлы/архивы.

## 3. Подготовка и публикация сборки через `pack-tool`

В репозитории лаунчера есть готовый CLI-инструмент `tools/publish/build-manifest.ts`.

### Шаг 1. Соберите файлы релиза

Пример команды (для сборки из `D:\CooodinG\Working\abi_tfg`):

```bash
npm run pack-tool -- ^
  --source "D:\CooodinG\Working\abi_tfg" ^
  --out "./out-release-tfg" ^
  --id "tfg-modern" ^
  --name "TerraFirmaGreg-Modern" ^
  --version "V0.13.19" ^
  --mc "1.20.1" ^
  --loader "forge:47.4.13" ^
  --repo "AbiBok89/abi_tfg" ^
  --tag "V0.13.19" ^
  --java 17 ^
  --memory 6144 ^
  --server "TerraFirmaGreg:abibok.20tps.ru:25565"
```

На Linux вместо `^` используйте `\`.

Инструмент исключает личные и временные папки (`saves`, `screenshots`, `logs`, `versions`, `libraries`, `.git`, `xaero`, `schematics` и т.д.), помечает `options.txt` / `servers.dat` как `mode: "initial"` (ставятся один раз при первой установке) и формирует:
- `out-release-tfg/release-assets/manifest.json`
- `out-release-tfg/release-assets/pack-part-01.zip` (и последующие части при необходимости)
- `out-release-tfg/release-assets/<sha>-<mod>.jar` (крупные файлы)
- `out-release-tfg/launcher/pack.json`

### Шаг 2. Создайте GitHub Release

1. В репозитории сборки откройте **Releases -> Draft a new release**.
2. Укажите тег, точно совпадающий с `--tag` (например, `V0.13.19`).
3. Перетащите **все файлы из `release-assets/`** (`manifest.json`, `pack-part-*.zip` и крупные `.jar`).
4. Опубликуйте релиз (не оставляйте в статусе Draft — черновики возвращают HTTP 404).

### Шаг 3. Обновите `launcher/pack.json` и `launcher/news.json`

1. Скопируйте `out-release-tfg/launcher/pack.json` в папку `launcher/pack.json` репозитория сборки. При необходимости добавьте `cover` (`"launcher/cover.png"` или https-ссылку) и `description`.
2. При необходимости добавьте новость в `launcher/news.json` (формат см. в `examples/pack-repo/launcher/news.json`).
3. Сделайте `git commit` и `git push` в ветку `main` репозитория сборки.

## 4. Правила обработки файлов на компьютере игрока

В манифесте для каждого файла задаются два флага:
- `mode: "managed"` (по умолчанию) — контролируется лаунчером:
  - при обновлении файла в сборке заменяется, если игрок его не менял;
  - если игрок изменил файл, при обновлении возникает конфликт с созданием резервной копии в `.abilauncher/backups/` перед заменой;
  - при исчезновении файла из новой версии манифеста удаляется автоматически, только если игрок его не изменял.
- `mode: "initial"` — устанавливается только при отсутствии на диске (например, `options.txt`), после чего принадлежит игроку и не перезаписывается.
- `required: true | false` — если `false`, при конфликте игроку разрешено выбрать «Оставить мою версию». Если `true`, несовпадение блокирует запуск до замены (с сохранением резервной копии).

> [!IMPORTANT]
> Хеши **SHA-256** в манифесте подтверждают целостность скачанных и локальных файлов (защищают от обрыва загрузки и случайных повреждений), но **не заменяют доверие к самому источнику** — если сам GitHub-аккаунт владельца скомпрометирован, злоумышленник сможет обновить и файлы, и манифест.

## 5. Что владельцу нужно заполнить перед первым использованием

1. **Репозиторий лаунчера (`AbiBok89/Abi_Launcher`)**:
   - Проверить [`catalog/catalog.json`](../catalog/catalog.json): перечислить все ваши репозитории сборок.
2. **Репозитории каждой сборки (например `AbiBok89/abi_tfg`)**:
   - Выпустить публичный GitHub Release с `manifest.json` и файлами сборки из `release-assets/` (сгенерированными через `npm run pack-tool`).
   - Поместить актуальный `launcher/pack.json` (или обновить `manifestUrl` в `launcher-index.json`, если используется старый формат) и `launcher/news.json`.
   - При необходимости загрузить обложку сборки (`launcher/cover.png` или `assets/bg-tfg.jpg`) и указать реальный `server` (`host`, `port`).
3. **Проверка ссылок**:
   - В тестовых примерах `examples/` используются демонстрационные плейсхолдеры `EXAMPLE_OWNER/EXAMPLE_PACK_REPO` и `mc.example.invalid` — перед публикацией собственной новой сборки обязательно замените их на свои реальные значения.

---

## 6. Обновление самого лаунчера (следующий этап)

Механизм обновления **сборок** полностью отделён от обновления **самого AbiLauncher**.
Автоматическое обновление приложения (например, через GitHub Releases + `electron-updater` с проверкой подписи релизов и отдельным каналом уведомлений в UI) вынесено в возможный следующий этап разработки и не смешивается с манифестами игровых сборок.
